# Core rules

Generated by tools/check-modules --write from the "Always-on rules" sections of
CONTRIBUTING.md and the modules. Do not edit by hand.

Read this file at the start of every task. Each heading links to the file that
explains its rules. Rules under a module that $MODULES does not enable do not
apply.

Rules marked [GATE] guard the named action. They apply in every mode, within the
scope of the task the user authorized, and they never turn a smoke test into
exhaustive validation. The other rules are standing preferences: when one
collides with a task's mechanics, work the mechanics out instead of stopping.

## [When editing kernel-agent-workflows](CONTRIBUTING.md)

- kernel-agent-workflows is generic, because it is public: no names of people,
  addresses, hosts, paths, accounts, credentials, machine details, employers,
  private mail, unposted work or dates. Personal facts go to a profile or an
  overlay ([details](CONTRIBUTING.md#everything-here-is-generic)).
- Before every commit to kernel-agent-workflows, run its tools/check-leaks and
  tools/check-modules, and read the diff for private facts, because the tools
  miss paraphrases.
- In kernel-agent-workflows, state each rule in exactly one module and link to
  it from elsewhere, so that a change lands in one place
  ([details](CONTRIBUTING.md#modules)).

## [core/evidence-discipline](core/evidence-discipline.md)

- A claim is either proven with evidence or reported as unknown, with more data
  gathered when the task needs the cause. Never fill the gap with a plausible
  story, even one that later turns out right, because a theory stated as the
  answer gets built into designs and patches.
- A root cause must fit every constraint of the report before it is called the
  cause, because a cause that misses one explains a different bug and is only a
  finding.
- Copy identifiers from their source: message IDs, URLs, commit IDs, and
  function and API names. When one can't be checked, describe the mechanism in
  general terms instead, because a reconstructed identifier is often subtly
  wrong and sends the reader to the wrong place.
- Settle every performance design choice by measuring the alternatives on the
  target machine, and measure an explanation of a result before stating it,
  because reasoning about performance is wrong often enough to miss the optimum
  ([details](core/evidence-discipline.md#performance-work)).

## [core/git-safety](core/git-safety.md)

- [GATE] Before a commit or amend: $COMMIT_WORD is in the user's instruction for
  the task, or the commit is a step of an instructed apply or a merge whose
  message the user confirmed, because the user decides what enters history.
  $COMMIT_WORD never authorizes applying patches to a publication tree.
- [GATE] Before a branch-structural operation: the user instructed this
  operation itself, even when a workflow seems to need it, because it rewrites
  or mixes branches that other people and trees build on.
- [GATE] Before resolving a conflict: the user saw the conflicted files and
  regions and asked for a resolution, even in auto mode, because a resolution
  decides how two lines of work combine. The one exception is a rebase of the
  agent's own patches during a rework the user asked for.
- [GATE] Before presenting a conflict or proposing its resolution: show where it
  came from, which commits on each side collide and how, and per commit how the
  resolution keeps its intention, auto-merged hunks included, because a check
  against the marked region or an earlier adaptation inherits whatever they
  missed.
- Add files to the index by name or pattern after reading `git status`, never
  with `git add -A` or `git add .`, because a working tree holds files that
  don't belong in the commit.
- Never `git stash`, and never pull or merge into a tree with uncommitted
  changes. Stop and ask instead, because a stash keeps work outside any branch
  and an aborted merge can take uncommitted changes with it.

## [core/overlays](core/overlays.md)

- Record a new rule or a correction from the user in the overlay of the module
  that owns the action, in the same session, because a correction that isn't
  written down gets repeated.
- Never edit a module of this repository for a lesson learned in use. It goes
  into an overlay first and reaches the module through a flush, because modules
  are shared and a change to one needs the generic review.
- After this repository is updated, rebase every overlay onto its changed
  module: the overlay's intention keeps priority and its wording and placement
  adapt to the new module, because the overlay records what the user decided
  ([details](core/overlays.md#after-an-update)).

## [core/publishing](core/publishing.md)

- [GATE] Before publishing: everything is prepared, the readiness summary showed
  the exact command, the user's most recent message contains $SEND_TOKEN as a
  standalone word, and the command runs exactly as presented, because what is
  published can't be recalled.
- A push to any remote others can read or that backs a pull request, the user's
  fork included, is publishing. The push of an instructed apply and the signed
  tag before a pull request don't wait for $SEND_TOKEN, because the instruction
  for those flows covers them.
- "Post", "send", "ship", "go ahead", "do it", "yes" and "ok" mean prepare and
  wait, because only $SEND_TOKEN approves publishing.
- Never run a publishing command expecting a permission prompt to stop it,
  because running the command is the publishing and the harness may allow the
  command without asking.
- Finish every step but the publishing command before asking for $SEND_TOKEN,
  because anything composed, pushed or assembled after the approval was never
  approved.
- The agent sends mail itself only when
  [mailbox/mail-send](mailbox/mail-send.md) is enabled, and otherwise hands the
  user the files and the command ([who sends
  mail](core/publishing.md#who-sends-mail)), because sending from the user's
  account is opt-in.

## [core/safe-operations](core/safe-operations.md)

- [GATE] Before a destructive or forced operation: look at the target, find out
  why the normal operation failed, and get the user's approval, because forced
  and destructive operations discard state that can't be recovered.
- Never re-run a state-changing command to inspect its result, because it acts
  again: a send sends again and a push pushes again. Inspect the resulting state
  instead.
- Never build, test or experiment in $PUBLICATION_TREES, because the user
  publishes from them and may be working in them live.
- Ask before every command that runs as root, showing the exact command, even
  when the request implies it, except on $ROOT_OK_HOSTS, because a privileged
  mistake on a shared machine can't be undone.
- Keep working files under $SCRATCH, never in /tmp or a per-session directory,
  because a remount or the end of a session loses them.

## [core/stop-and-ask](core/stop-and-ask.md)

- Solve mechanics and stop only for genuine blockers, because asking about a
  solvable problem wastes the user's time and guessing past a blocker does
  damage.
- When stopping, never hide the problem by skipping, narrowing or forcing a
  step, because the user decides what to do next from what actually failed.

## [core/validation-scope](core/validation-scope.md)

- Size validation to the decision it supports: choose the coverage, the
  confidence and an effort budget before starting, because checks grown without
  a target turn into a separate project.
- Verify a feature with the quickest adequate check. Existing tests, small
  scripts and temporary probes are fine, because framework integration and
  submission-ready tests are separate work that the user asks for.

## [core/waits-and-long-ops](core/waits-and-long-ops.md)

- Run long operations one at a time and verify each before starting the next,
  because a second operation started on a failed one wastes its run and hides
  the failure.
- Every wait has a deadline and checks progress against ground truth, never
  against what the job or sub-agent reports about itself, because a stuck job
  and a slow one look the same from outside.
- Read the output of every background command and confirm that it succeeded
  before going on, because a silent failure looks like silent success.

## [patches/comments-kerneldoc](patches/comments-kerneldoc.md)

- A comment states what the code can't show: the contract, the invariant, the
  constraint or the reason behind a non-obvious choice. Never a narration of the
  code, because narration goes stale with the code and buries the fact the
  reader needs.
- A comment gets its final wording in the patch that introduces it, because a
  rewrite by a later patch in the same patchset makes reviewers read it twice
  and leaves interim text in the history.
- [GATE] Before committing a patch: no added comment narrates the code or refers
  to sibling patches or future plans, and every added kerneldoc summary is
  capitalized, because stale comments mislead and one summary form keeps
  kerneldoc easy to scan.

## [patches/commit-tags](patches/commit-tags.md)

- Refer to a commit in prose as `<sha12> ("subject")`
  ([form](patches/commit-tags.md#commit-references)), never by a bare ID,
  because the subject tells the reader what the commit is and lets them check
  the ID.

## [patches/cover-letters](patches/cover-letters.md)

- Nothing local goes into a cover letter or anything else an outside reader
  sees: machine names and sizes, local config options, the names of local test
  suites, tests held back from the posting, or what ran on which machine,
  because the reader can't use any of it.

## [patches/line-widths](patches/line-widths.md)

- Fill descriptions, comments and code to $WIDTHS in both directions: no line
  over its limit, and no line that could still take the first word of the next
  line, because a paragraph broken short leaves a ragged edge that the next edit
  reflows, which puts unrelated line changes into that later patch.
- Check widths with tools/textfill, never by eye, because fills checked by eye
  drift no matter how often the rule is written down.
- [GATE] Before committing a patch: `textfill check` passes on the staged draft,
  and the edited text was reflowed, scoped and kept ASCII, because a fill fixed
  after the commit needs an amend.
- [GATE] Before posting a patch or patchset: `textfill check` passes on every
  patch, exported into a new, empty directory, because a check of the patch just
  edited misses text written earlier.

## [patches/patch-descriptions](patches/patch-descriptions.md)

- A description says why, not what: who needs the change and why, what it
  guarantees, and what a reviewer needs to check it, because the diff already
  shows what changed.
- A description stands alone in the git history: no names of sibling patches and
  no "this series", because the patchset around it is gone once it is merged.
- [GATE] Before committing a patch: the subject follows the tree's convention,
  the description doesn't narrate the diff, and neither the subject nor the body
  uses kerneldoc `%` markup, because a maintainer has to fix each by hand or
  send the patch back.

## [review/checkpatch](review/checkpatch.md)

- checkpatch is advisory: report its findings and never change a patch for one
  without asking, because many of its warnings are false positives.

## [review/formal-model-check](review/formal-model-check.md)

- With `$FORMAL_MODEL` on, every multi-actor shared-state protocol a patchset
  adds or changes gets a model check, because reading misses rare interleavings.
- [GATE] Before trusting a model result: it failed a falsification run and its
  traces replay on the C, because a weak model passes and a wrong one fails.

## [review/kernel-build](review/kernel-build.md)

- [GATE] Before testing, posting or applying a code change: build it with
  `$BUILD`, the kernel first and then every tool and selftest it touches, and
  report every warning and error, because a change nobody built breaks the build
  for everyone who pulls it.
- Run every build stage through `$BUILD`, never another make command, because
  the .config and the build artifacts come from `$BUILD`'s compiler and options,
  and a stage built another way mixes the two.

## [review/patchset-review](review/patchset-review.md)

- Review at milestones: one batch review when a coherent batch is ready for
  broader testing or for posting, never one per patch, edit or commit update,
  because a review per edit slows the work and a correction gets a focused check
  instead.
- Skip the milestone review only when the user says "skip review", because it
  catches what building and testing miss before the batch moves on.
- Judge a finding about patch N against the tree with patches 1..N applied,
  never the final tree, and report one that a later patch resolves as "valid at
  N, resolved by N+k", because every patch has to build and work on its own for
  bisection.
- Sub-agents inherit the parent's model. Never set a different one, because the
  user chose the model for the work, and a smaller one misses what the parent
  would find.

## [mail/lore-thread](mail/lore-thread.md)

- Read every message of a thread before reporting on it. Never filter by an
  assumed sender, because a bot's review counts like a person's.
- Report a message or a reply as missing only after reading the relevant threads
  end to end, because a search that finds nothing says something about the
  search, not about the mail
  ([core/evidence-discipline](core/evidence-discipline.md#what-counts-as-evidence)).

## [mail/mail-compose](mail/mail-compose.md)

- [GATE] Before mail files leave the agent: the files and the send command pass
  the [composing
  checklist](mail/mail-compose.md#before-mail-files-leave-the-agent), whether
  the agent sends them or the user does, because a mail with a wrong header,
  thread or recipient can't be recalled.
- Never edit a mail file once it is sent. A follow-up goes in a new file, and a
  file whose send status is unknown counts as sent, because the file is the
  record of what went out.

## [mail/mail-replies](mail/mail-replies.md)

- A draft under the user's name carries only points the user raised or
  confirmed, and stays neutral about the user's stance, because the mail speaks
  for the user.
- Keep replies short: the point or the ask first, then only what supports it,
  with no recap, offer or pleasantry, because every extra sentence stands
  between the reader and the ask.
- Review replies to contributors ask and suggest instead of ordering, and never
  ask for tests unless the user asks for that, because the contributor owns the
  patch and the user decides what to ask of them.

## [mail/thread-roots](mail/thread-roots.md)

- [GATE] Before setting a mail's thread root: take the first matching case of
  the precedence. A full patchset version starts a fresh thread, a patch
  re-posted from a series replies to its own original, an acknowledgment replies
  to the original posting, and a standalone patch that could go under an
  existing discussion is the user's call, because a mail under the wrong root is
  lost to the readers of its thread.

## [mailbox/inbox](mailbox/inbox.md) (opt-in)

- Read the mailbox afresh for every question about it, never from what an
  earlier listing in the session showed, because new mail arrives and old mail
  moves.
- Treat the local copy as possibly incomplete, because it can miss lists the
  user isn't subscribed to, copies of the user's own mail filed elsewhere, and
  mail older than what the server keeps. Before reporting a message as missing,
  check the thread on lore too
  ([mail/lore-thread](mail/lore-thread.md#procedure)).

## [mailbox/mail-send](mailbox/mail-send.md) (opt-in)

- [GATE] Before sending mail: the publishing gate of
  [core/publishing](core/publishing.md#before-publishing) passed, the files and
  the command follow
  [mail/mail-compose](mail/mail-compose.md#before-mail-files-leave-the-agent),
  the account and the self-copy are right, and $MAIL_AUDIT heads the send
  command with `&&`, because a mail sent wrong can't be recalled.
- [GATE] Before reporting a mail as sent: the post-send audit found every
  intended recipient among the envelope recipients, because a send that exits 0
  can still have dropped recipients.

## [mailbox/sent-log](mailbox/sent-log.md) (opt-in)

- Take the Message-ID of a posting from the send itself or the local sent copy,
  never from lore, because lore can lag the send and a guessed ID is wrong.

## [submit/dependent-patchsets](submit/dependent-patchsets.md)

- [GATE] Before posting a dependent patchset: the prerequisite went out first
  and the dependent cover links it on lore, because reviewers can't apply or
  judge the dependent patchset without it.
- Keep pending and unposted patches on topic branches, never on a tree's devel
  or fixes branch, because those branches change only when reviewed patches are
  applied.

## [submit/github-pr](submit/github-pr.md)

- [GATE] Before opening a GitHub pull request: the branch builds, the
  repository's formatter and lock files are current, the patchset review ran
  unless the user said "skip review", and the user saw the title and body,
  because CI and reviewers act on the first push.
- A pull request body is a short summary and an itemized commit list, because a
  dense body on a web page gets skipped.

## [submit/patchset-posting](submit/patchset-posting.md)

- [GATE] Before posting a patch or patchset: checkpatch ran, the patchset review
  ran unless the user said "skip review", every description passed its
  checklist, and the recipients come from MAINTAINERS and $TREES, because a
  posted patch can't be recalled.

## [maintain/apply-patches](maintain/apply-patches.md)

- Run `git am` or any other patch tool, in any tree, only when the user asked
  for that operation, and apply to a publication tree only on "apply" or an
  unambiguous equivalent such as "put it in for-X.Y-fixes". A posted patch waits
  for that word, because the user decides what enters a tree.
- [GATE] Before applying a patch: the thread was read, the patches were
  reviewed, no other tree took them, and the user approved the patches and the
  target branch, because undoing a wrong apply on a published branch takes a
  force push or a revert.
- [GATE] Before pushing applied patches: every commit message was read in full
  and has exactly one Signed-off-by from $IDENTITY, plus the author's on a
  contributor patch, and the build passed, because a missing committer sign-off
  on a public branch violates the DCO.
- Push the applied branches without a pause to confirm, because the apply
  instruction covers the push and the server rejects a push that doesn't
  fast-forward.
- Acknowledge every apply, the user's own patches included, under the gate of
  [core/publishing](core/publishing.md#before-publishing), because the thread
  learns where the patches went only from the acknowledgment.

## [maintain/branch-model](maintain/branch-model.md)

- Take the release cycle from $TREE_STATE and branch names from the tree's own
  clone in $TREES, never from memory or from a same-named branch in a scratch
  tree or worktree, because the rc changes every week and a stale copy of a
  branch hides work that already landed.

## [maintain/merges](maintain/merges.md)

- [GATE] Before committing a merge: conflicts were resolved from the commits on
  both sides and verified on every path, and the user confirmed the message
  unless it is git's default one for for-next, because a resolution read from
  the 3-way diff alone can build and still drop a change.
- Never resolve a conflict on for-next. Abort, resolve in the devel branch and
  merge that into for-next, because for-next is rebuilt freely and must stay a
  plain union of the real branches.

## [maintain/pull-request](maintain/pull-request.md)

- [GATE] Before creating a pull request tag: the base, the commits, the
  test-merge build, the names and the diffstat were verified, because a
  published tag can never be moved or deleted.
- [GATE] Before sending a pull request: the tag is pushed, `git request-pull`
  exits 0, and the mail body is its output verbatim, because mainline pulls
  exactly what the public tag holds, and a failing request-pull means the tag
  there doesn't match.

## [test/machine-access](test/machine-access.md)

- Reach a test machine through the mechanism `$MACHINES` names for it and the
  capability, and ask the user when it names none, because an improvised path
  can act on the wrong machine or lose the state the named one preserves.
- Read access credentials from a secret store or a file at the moment of use.
  Never put them on a command line, in a script or in an overlay, because
  command lines show up in process lists and transcripts, and files get copied.

## [test/perf-comparison](test/perf-comparison.md)

- [GATE] Before comparing performance: both variants ran on bare metal, on
  performance kernels without debug instrumentation built from the same
  configuration (one kernel for userspace variants), with the effective
  configuration, the identity and the boot options verified and saved, because a
  VM or a debug kernel measures the host and the instrumentation, not the
  change.
- Measure the metric that the mechanism changes, never a system-wide metric that
  unrelated factors dominate, because a tangential metric hides the effect in
  noise.

## [test/remote-testing](test/remote-testing.md)

- [GATE] Before a kexec, reboot, power cycle or kernel deploy: a console monitor
  is running and capturing. A test kernel has also passed its build and boots by
  kexec or a one-shot boot entry, never as the default, because only the console
  records a boot or a crash that ssh can't reach, and a remote power cycle must
  bring back a kernel that works.
- [GATE] Before starting a test on a test machine: the console monitor is still
  capturing, the machine runs the kernel just built with kdump loaded where it
  has kdump, and the test is a script file, because a kexec can end the monitor
  and drops the crash kernel, and results from a stale kernel prove nothing.
- [GATE] Before reporting test results: the console was reviewed for the whole
  run, the logs were copied off the machine and show no setup failures and every
  positive marker, every planned iteration is accounted for, and machines that
  are expensive to leave idle are off once no more runs are planned, because a
  test that ran nothing also exits 0 with no warnings, and a partial run
  reported as a pass hides what was never tested.
- Edit and build on the workstation and run on the test machine. Never build on
  a test machine or copy files that a shared filesystem already shares, because
  the build setup lives on the workstation and a copy goes stale.
- Never edit a script while a test machine runs it, because bash reads a script
  while it runs and executes the edited text.

## [debug/bug-report-triage](debug/bug-report-triage.md)

- Code inspection alone never confirms a reported bug. Every fix needs a runtime
  signal that fires before it and is gone after it, because a report can quote
  the right code and still rest on one misread line.
- Reproduce a race by widening its window, never by forcing a state the real
  code never produces, because a forced state proves only the forcing.
- Triage a batch one finding at a time, with the user confirming each verdict,
  because a reproducer and fix built on an unconfirmed verdict are wasted when
  the verdict is wrong.
- [GATE] Before posting a fix patchset from a triage: record each patch's
  reproducer tier in the verification table, because reviewers rely on it.

## [debug/crash-debugging](debug/crash-debugging.md)

- SysRq-c keeps a hung machine's state through kdump, and a power reset destroys
  it. Never use one in place of the other, because the choice decides whether
  the failure can be analyzed.
- [GATE] Before triggering a crash with SysRq-c: the console monitor is
  capturing and kdump is loaded, because the crash ends the running kernel, and
  the console log and the dump are then the only records of its state.
- [GATE] Before a power reset: the console log was saved and reviewed, a crash
  dump was captured or can't be triggered, and the user accepted losing the
  diagnostic data, because a power reset destroys the state that explains the
  failure ([what counts](debug/crash-debugging.md#power-resets)).
- [GATE] Before analyzing a crash dump: drgn opens the vmcore, the vmlinux is
  from the same build as the crashed kernel, and dmesg was extracted first,
  because a mismatched vmlinux gives wrong types and stacks without an error.

## [debug/event-tracing](debug/event-tracing.md)

- When kernel behavior needs a causal answer, add probes and read the data
  instead of reasoning from incomplete data, because a probe round takes
  minutes.
- Keep debug probes, trace rings and triggers in a separate debug commit that is
  never posted or merged, because they are temporary.
- [GATE] Before trusting probe data: confirm that each probe exists in the
  running kernel and sees its arguments, that no output waits for program exit,
  and that ring writers can't collide, because each failure loses or corrupts
  data without an error.
